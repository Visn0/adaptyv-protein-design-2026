# Site-sync playbook (ch5)

Purpose: the challenge-5 website must never lag behind the work. Any agent
(cron or subagent) doing a site sync follows this playbook.

## The site's architecture (single source of truth)

- `challenges/05-pmhc/lineage.json` — generated by
  `challenges/05-pmhc/scripts/work/build-lineage.py`. It holds every
  experiment (id, title, verdict, summary, goal, verdict_detail, chapters,
  viewer list, proteins). The serve app renders the challenge page and the
  per-experiment lineage pages from it.
- `challenges/05-pmhc/viewers/multiview/<exp>.html` — generated by
  `challenges/05-pmhc/viewers/scripts/make_molstar_multiview.py <exp-id>`.
  FOLD_SETS lists the fold trees it can read.
- The live app: `PYTHONPATH= .venv/bin/python -m tools.cli serve` on port
  8737 (usually already running; if not, start it detached and leave it up).

## The sync procedure

1. `git -C ~/Projects/adaptyv-protein-design-2026 status --porcelain challenges/05-pmhc`
   and `find challenges/05-pmhc/{records,notes,scripts/work} -newer
   challenges/05-pmhc/lineage.json` — this is what changed since the last
   build. The evolution loop writes outside the repo: also check
   `ls -dt ~/c5-work/evo/gen*` (a generation folder newer than lineage.json
   is new work) and `tail -20 ~/c5-work/evo/autopilot.log` (lines
   `AUTOPILOT genN done` and `AUTOPILOT complete` give the state; a
   generation whose folder is newer than lineage.json is unrecorded).
   The sync itself edits this playbook and site-sync-todo.md, so a digest
   whose only entries are those two notes still needs the ~/c5-work/evo
   checks above.
2. For every new/changed artifact, find the matching experiment in
   `build-lineage.py` (`records/cN-*/README.md`, `notes/*.md`, new scripts or
   campaigns). Update that experiment's summary/verdict/chapters/verdict_detail
   with the NEW facts (numbers, verdicts, dates). Keep the house style: ASCII
   only, no em dashes, terse, honest about negatives.
3. New campaign? Add a full `add(...)` block (id, title, date, verdict,
   best, scores, summary, goal, goal_extra, verdict_detail, chapters) and a
   VIEWERS entry with 3 fold names that exist in a FOLD_SETS tree.
4. Rebuild: `PYTHONPATH= .venv/bin/python
   challenges/05-pmhc/scripts/work/build-lineage.py` then the viewer
   generator for every changed experiment id.
5. Verify: curl the challenge page and each changed lineage page on
   http://127.0.0.1:8737 (expect HTTP 200 and the new text present).
6. Commit with explicit paths ONLY (never `git add -A` — another agent shares
   this repo). Another agent may have files staged in the index, and a bare
   `git commit` (no pathspec) commits those too. Commit with
   `git commit --only challenges/05-pmhc/<paths> -m "..."` (or check
   `git diff --cached --name-status` first), then push. Check
   `git show --stat HEAD` shows only intended files.
7. Ambiguous or unfinished work: do NOT invent. Append a dated bullet to
   `challenges/05-pmhc/notes/site-sync-todo.md` and leave the site unchanged
   for that item.

## Hard rules

- The app stays local. The public site is the static export, deployed by
  GitHub Actions only (`site/PLAN.md`).
- Never print values from `.env`; source it only if a tool needs it.
- One GPU job at a time; the site sync itself needs no GPU.
- The final response of a sync run: max 6 lines — what was added/changed,
  what was skipped and why, what was committed (hash).
